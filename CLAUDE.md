# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is an unofficial Home Assistant custom integration for Rivian vehicles. It uses the `rivian-python-client` library to communicate with Rivian's cloud API via GraphQL subscriptions and REST endpoints. Beyond live vehicle state, it includes a trip efficiency/analytics subsystem that reconstructs and stores per-drive statistics (distance, efficiency, MPGe, DC fast-charge sessions, weather correlation) and can generate a turnkey Lovelace dashboard for them.

Install target is HACS (custom repository) or manual copy into `custom_components/rivian`; `hacs.json` and `requirements.txt` both set the Home Assistant floor at `2025.1.0`; `manifest.json` pins only `rivian-python-client`. Remote vehicle control (lock/unlock, climate, etc.) requires 2FA on the Rivian account and Bluetooth pairing, and is **not supported on Gen2 (2025) vehicles** due to BLE hardware changes.

## Development Commands

### Setup (in devcontainer or local)
```bash
pip install -r requirements.txt
pre-commit install
```

### Linting
```bash
ruff check custom_components/
ruff format custom_components/
```
Ruff config lives in `pyproject.toml` (`[tool.ruff]`, requires `>=0.16.2`): `RUF012` is ignored (mutable class attrs don't need `ClassVar`), and isort is configured with `force-sort-within-sections`, `known-first-party = ["homeassistant", "tests"]`, `forced-separate = ["tests"]`. A `[tool.pylint]` section also exists but nothing invokes pylint. `.github/workflows/ci.yaml` runs ruff and pytest on PRs and pushes to `main`; pre-commit (`.pre-commit-config.yaml`) runs `ruff check --fix` and `ruff format` locally.

Invoke tooling as `python -m ruff` / `python -m pytest` so it runs under the project's interpreter even where the tools' scripts aren't on PATH.

### Tests
```bash
pytest                          # run full suite
pytest tests/test_drive_storage.py::test_name   # single test
```
Tests live in `tests/` and use plain `pytest` (not `pytest-homeassistant-custom-component`); `tests/conftest.py` hand-rolls async test support (`pytest_pyfunc_call`) plus mocks like `SubscriptableMock`/`DynamicEnum` in place of a real HA test harness. `pytest` is not pinned in `requirements.txt` — install it separately (`pip install pytest`), as CI does. Notable fixture: `tests/fixtures/r1s_10day_history.db`, a real SQLite recorder database used to test the history-backfill feature.

## Architecture

### Core Components

**Entry Point (`__init__.py`):**
- Sets up coordinators and forwards platform setup
- Creates `UserCoordinator` first to get vehicle list
- Creates a `VehicleCoordinator` per vehicle
- Creates a single `WallboxCoordinator` for all wallboxes
- Stores per-entry objects in `hass.data[DOMAIN][entry_id]`. The shared `AnalyticsDatabase`, its setup lock, the WebSocket-registration flag, and the zone-change-listener registration flag/remover sit beside them under underscore keys (`_analytics_db`, `_analytics_db_lock`, `_ws_api_registered`, `_zone_listener_registered`, `_zone_listener_remove`, plus the demo registry's `_demo_stores` and `_demo_vehicles`), so iterate config entries with `_iter_entry_datas()`, which skips them -- that skip is also what keeps demo stores out of every zone/retention/service loop
- After the platforms are forwarded, `_schedule_dashboard_autocreate` runs `_async_auto_create_dashboard` once per instance (after HA has started) to create the "Rivian" dashboard when the HA `Store` flag `rivian_dashboard_autocreate` is unset, Lovelace is in storage mode and no `rivian-dashboard` exists; it sets the flag also when the dashboard exists (a later delete is never undone), and in YAML mode only posts a persistent notification. Failures log a warning, never fatal; a brand-new dashboard still needs one restart for the sidebar (Lovelace's dashboards collection is private)
- Registers each bundled card in `frontend/` (Plotly, Mushroom, `rivian-series-card`) as a static path and Lovelace resource for the efficiency dashboard
- Reads HA's configured zones (`drive_storage.read_zone_states`) and syncs them into every VIN's places at setup, then again on any `zone.*` state change (a process-wide listener registered once, debounced 10 s via `async_call_later`)
- Registers and unregisters the custom services described below

**Data Coordinators (`coordinator.py`):**
- `RivianDataUpdateCoordinator` - Abstract base with error handling and exponential backoff
- `UserCoordinator` - Fetches user info and vehicle list
- `VehicleCoordinator` - Subscribes to real-time vehicle state updates via WebSocket
- `ChargingCoordinator` - Polls charging session data (adjusts interval based on plugged-in status)
- `DriverKeyCoordinator` - Fetches driver/key enrollment data
- `WallboxCoordinator` - Polls wallbox data
- `VehicleImageCoordinator` - Fetches vehicle images on-demand

**Entity Base Classes (`entity.py`):**
- `RivianEntity` - Generic base
- `RivianVehicleEntity` - For vehicle sensors/binary sensors
- `RivianVehicleControlEntity` - For commands (checks gear=park, zone restrictions, pairing status)
- `RivianChargingEntity` - For charging session data
- `RivianWallboxEntity` - For wallbox data

**Entity Descriptions (`data_classes.py`):**
Custom dataclasses extending HA entity descriptions with Rivian-specific fields like `field` (API field name), `value_lambda`, `on_value`, etc.

**Sensor Definitions (`const.py`):**
Dictionaries `SENSORS` and `BINARY_SENSORS` keyed by vehicle type ("R1", "R1T", "R1S") containing entity descriptions. The trip-analytics sensors are kept separately in a flat `DRIVE_SENSORS` tuple (not keyed by vehicle type), instantiated as `RivianDriveSensorEntity` and fed by the drive tracker below.

### Data Flow

1. Vehicle state comes via WebSocket subscription (not polling)
2. `VehicleCoordinator._process_new_data()` receives updates and merges with existing data
3. Invalid sensor values are filtered out using `INVALID_SENSOR_STATES`
4. Entities read values via `coordinator.get(field_name)`

### Trip Efficiency & Analytics Subsystem

This is a separate live-tracking + historical-reconstruction layer built on top of vehicle state, spread across several modules. "Segment" means one drive within a day (a coming feature); the fixed 3-minute efficiency pieces are "chunks" (closed every ≥180 s, with a final chunk kept only if ≥90 s), and the only remaining "segment" spellings for chunks are legacy-compatibility reads (the pre-rename JSON import fallback, the WebSocket `"segments"` alias, the schema-1 checkpoint keys, and the v4 migration).

- **`drive_models.py`** - Shared dataclasses and constants: `DriveRecord`, `DriveChunk`, `ChargingSample`, `ChargingSessionRecord`, `VampireDrainRecord`, `SpeedBinData`, plus tuning constants (`MPGE_FACTOR`, `STANDARD_SPEED_BINS`, `MICRO_DRIVE_THRESHOLD_MILES`, `DCFC_MIN_POWER_KW`, `MAX_DCFC_HISTORY_SESSIONS`). `DriveRecord` also carries the optional, Strava-style per-drive fields below (all `None`/empty when not computed): track-derived `moving_seconds`, `stopped_seconds`, `stop_count`, `climb_ft`, `descent_ft`, `track_max_speed_mph` (a robust 99th-percentile max, distinct from the live `max_speed_mph`), `pct_distance_over_70mph`; and live vehicle-context `start_range_mi`/`end_range_mi`, `drive_modes` (list, first-appearance order), `trailer` (bool), `driver`. `trailer_status_to_bool`/`trailer_attached_any` map Rivian's `trailerStatus` values (undocumented publicly; "connected"/"attached" vs. "not_connected"/"disconnected"/"unknown"/etc, unrecognized -> `None`).
- **`energy_model.py`** - Pure-Python anchored efficiency model.
  - **Measured points:** each spans at least a 0.3% SoC drop (`MEASURE_MIN_SOC_DROP_PCT`; one 0.1% step is only ~0.3 mi and too jittery) and sits at its interval's distance midpoint.
  - **Curve:** worked out in kWh/mi, which stays finite when the modelled energy nears zero. It's the measured values interpolated in time, plus `SHAPE_WEIGHT` (0.5) × the physics model's (aero, rolling, grade, kinetic, aux) deviation from its own value at the measured points, over ~1 km windows (`SHAPE_WINDOW_M`). It therefore passes exactly through every measured point.
  - **Fit:** `fit_params` fits CdA, Crr, aux and η_regen per vehicle. `AnalyticsDatabase.fit_energy_model(vin)` uses the last 90 days of routed drives and needs at least 15; otherwise it keeps the previous fit. The fit is stored in `meta` as `energy_model:<vin>`.
  - **Refit:** nightly on the retention timer, after setup when no fit exists, and on demand via `rivian.fit_energy_model`.
- **`drive_conditions.py`** - Pure-Python (stdlib only) driving conditions for the Efficiency page. A weather sample is a dict with `t` (POSIX s) or ISO `timestamp`, and any of `temp_f`, `wind_speed_mph`, `wind_dir_deg` (where the wind blows **from**), `pressure_hpa`, `precip_mm`, `humidity_pct`; a missing field just doesn't contribute. `headwind_component(track, samples)` is the distance-weighted headwind in mph, **positive = headwind**: per track piece (skipping <8 m, >120 s gaps and >60 m/s glitches) the initial bearing is the heading, the time-nearest wind sample supplies speed x `WIND_HEIGHT_FACTOR` (0.75, a log-law scaling of Open-Meteo's 10 m wind to ~2 m vehicle height) and the component is `speed * cos(wind_from - heading)` (so north-bound into a north wind is +, a crosswind ~0, an out-and-back ~0). `make_headwind_fn` gives the same per interval in m/s for the energy model. `air_density(temp_c, pressure_hpa, rh_pct)` is moist air (Tetens + dry/vapour partial densities; 15 C / 1013.25 hPa / dry = 1.225 kg/m^3; missing humidity = 50%). `summarize_conditions` reduces a drive to `wind_speed_mph`/`wind_dir_deg` (distance-weighted mean wind **vector**, so opposing legs cancel), `headwind_mph`, `precip_mm` (mean sample rate x drive hours, an estimate), `pressure_hpa`, `humidity_pct`, `air_density`; `compute_condition_columns` adds `expected_kwh`; `archive_samples` turns Open-Meteo archive hours into samples bracketing a drive.
  - **Expected energy:** `energy_model.expected_battery_kwh(track, params, distance_miles, rho, headwind_fn)` is the fitted model's battery kWh over the route. `interval_features` gained optional `headwind_fn` (airspeed = ground speed + headwind, sign kept) and takes `rho` as before; with neither it is bit-identical to before. It scales up for GPS gaps and returns `None` when intervals cover <80% of the drive. It uses the VIN's `get_energy_model` fit, else `DEFAULT_PARAMS`, with the drive's own air density and headwind. **Score = `expected_kwh / energy_kwh`, computed on read** (>1 = used less than the model expected). `expected_kwh` is stored add-only and not recomputed on a refit.
- **`drive_stats.py`** - Pure-Python (stdlib only) `compute_track_stats(track) -> TrackStats`: the Strava-style per-drive stats computed once from a completed drive's GPS route. Moving/stopped time comes from per-fix speed (falling back to distance/time when speed is missing); a gap between fixes over 120 s counts as neither. `stop_count` is maximal stopped runs ≥20 s, excluding one touching the track's very start or end. Climb/descent use a 4 m hysteresis zig-zag filter on altitude so GPS noise doesn't inflate them. Max speed is the 99th percentile of point speeds (spike-resistant), not the raw max. All fields are `None` when the track has <2 points or lacks the needed column. There is deliberately no regen stat: the SoC Rivian reports doesn't rise during regenerative braking (on 53 real routes only 5 of 8,089 readings rose, each a 0.1% flicker), so regen can't be derived from the route.
- **`drive_tracker.py`** - `DriveTracker`, the real-time drive lifecycle engine. Watches live vehicle state (gear, speed, GPS) to detect drive start/stop (with park debounce), bins speed samples, samples weather every ~15 miles / 20 minutes via `weather.py`, and detects DC fast-charge sessions. It also records the drive's GPS route (one point per new `gnssLocation.timeStamp`, ~5 s apart) and checkpoints the in-progress drive to SQLite every 30 s and on unload/HA stop. On setup it resumes a fresh checkpoint if the car is still in gear, and otherwise finalizes it at the last recorded point, so a restart or options reload mid-drive no longer loses the drive. Checkpoint `schema` is 3: on top of schema 2, it adds the live-captured vehicle context (`distanceToEmpty` -- reported in **kilometres**, converted to miles for storage/`DriveRecord`; `driveMode` mapped through `DRIVE_MODE_MAP` for display; `trailerStatus`; `activeDriverName`), sampled on drive start and every telemetry update; the deserializer still accepts schema 1 and 2, defaulting the new keys to `None`/`[]`. At finalize, `compute_track_stats` runs against the drive's captured track (if any, and never fatally) to fill the track-derived `DriveRecord` fields. Charging: `_finalize_active_charge_session` classifies a session as DC when its real peak power, its average power (estimated from the SoC rise when the vehicle reports no power; an estimated *peak* is too noisy to classify on) or its energy/duration rate reaches `DCFC_MIN_POWER_KW`; a slower one is kept as `kind='ac'` only if it gained at least `AC_SESSION_MIN_SOC_GAIN_PCT` (1 %) and lasted `AC_SESSION_MIN_DURATION_S` (5 min), with at most `AC_SESSION_MAX_SOC_POINTS` (20) coarse SoC samples (power 0, via `charging.coarse_soc_samples`) and no curve. The session start's `gnssLocation` is captured as `lat`/`lon`, and the DB assigns its place at upsert.
- **`drive_track.py`** - Pure-Python GPS route model (`DriveTrack`/`TrackPoint`, SI units): validation, Douglas–Peucker `simplify`/`preview`, and a versioned, columnar, delta-encoded JSON `encode`/`decode`.
- **`road_heat.py`** - Pure-Python (stdlib only) road heat map on a fixed Web Mercator grid at `BASE_LEVEL` 21 (~14 m cells at 44°N). `track_passes(track)` walks the line between fixes cell by cell (exact grid traversal; GPS glitches skipped) and counts **passes**, not drives: a drive that comes back to a cell counts again (an out-and-back counts twice), but only after being away over `REPASS_MIN_GAP_S` (120 s) **and** driving over `REPASS_MIN_DISTANCE_M` (200 m), so bunched fixes, parking-lot loops and long stops never double count. Each cell gets two counts: passes *through* it and passes *near* it (within `CORRIDOR_RADIUS` = 1 cell). `RoadHeat` stores both. `RoadHeat.display()` draws only cells some drive passed through, each colored by its near count, because a road's two directions of travel and GPS drift split one road's passes across neighbouring cells (a plain count showed a road driven 20 times as a mix of 8s and 20s); measured on real drives, a radius of 2 found only ~1% more. Counts are per drive, so months sum exactly into a year or all time. `HeatGrid.tile(z, x, y)` serves one XYZ tile, coarsening finer cells by MAX (never sum). Rows record `HEAT_FORMAT_VERSION`; `update_heat` recounts a VIN's months once when its heat came from an older format (tracked in `meta` as `road_heat_format:<vin>`).
- **`road_snap.py`** - Road-snapped GPS gap filling. Rivian's live stream sometimes drops mid-drive, leaving a stored route with a straight-line jump across the outage; this module reconstructs a plausible path along real roads instead. `find_gaps(track)` flags consecutive fixes over 300 m *and* 30 s apart (excluding `road_heat._is_glitch` jumps, which are bad GPS, not a dropout). For each gap, `gap_bbox`/`bbox_area_m2`/`bbox_key` build a padded bounding box (skipped if over ~100 km²) and `build_overpass_query`/`parse_overpass` fetch and parse `way["highway"]` data (footway/cycleway/path/steps/pedestrian/track/parking-aisle service ways excluded) from the public Overpass API via `async_fetch_roads` (HA's shared aiohttp session, a clear User-Agent, 20 s timeout, rate-limited to 1 request/5 s process-wide; any network/parse error returns `None`, meaning "unknown", never "no road"). `snap_gap(gap, ways)` is pure CPU: both endpoints must snap within 50 m of a road (respecting `oneway`), a Dijkstra path between them must be at most 1.6x the straight-line distance and imply at most 45 m/s, and the accepted path is resampled every ~50 m with time/altitude interpolated between the gap's own two fixes (speed = path length / gap time; soc/odo left `None`).
- **`places.py`** - Pure-Python (stdlib only) favorite-places logic: frequent drive start/stop spots become named "places" so a drive reads "Home → Work". `drive_endpoints(rows)` turns a VIN's time-ordered drives into start/end points using the same parked-position rule `day()` uses (a drive's start snaps to the *previous* drive's end when that lies within `DAY_GAP_MAX_M` (3000 m, mirrors `analytics_db.DAY_GAP_MAX_M`) of its own recorded start). `cluster_endpoints(endpoints, fixed_places, existing_auto)` greedily clusters points not already inside a zone/user place (a hidden zone/user place still "owns" its points, so they're never clustered elsewhere) within `CLUSTER_RADIUS_M` (200 m), centroid updated as the running median; a cluster reaching `MIN_VISITS` (3) becomes a place, matched back to an existing `auto` place within its radius so ids/hidden/name/category/geocode state survive a rebuild. `assign(point, places)` returns the nearest *non-hidden* containing place's id (hidden places label nothing). `place_label(name, geocode_name, place_id)` is `name` else `geocode_name` else `"Place #N"`. **Shared, not per vehicle (schema v10):** places belong to no vehicle, only to a `dataset` (`DATASET_REAL`/`DATASET_DEMO`; the only partition, so demo places never label or mix with real ones). `pooled_endpoints(rows_by_vin)` runs the parked-position chaining per vehicle (a drive's start only snaps to the *same car's* previous end) and then pools every car's endpoints (time-merged) for `cluster_endpoints`. `PLACE_CATEGORY_DEFS` (key, label, mdi icon) is the one source of truth for categories (home, work, school, shop, dining, charging, friends, family, gym, swim, mountain_biking, park, medical, other): `PLACE_CATEGORIES` is its keys (WebSocket validation), `category_options()` is `[{key,label,icon}]` for the cards.
- **`geocode.py`** - Reverse-geocodes an auto-detected place's coordinates via the public OSM Nominatim API, mirroring `road_snap.async_fetch_roads`'s HTTP pattern (HA's shared aiohttp session, a clear User-Agent, 20 s timeout, rate-limited to 1 request/s process-wide per Nominatim's usage policy). `async_reverse(hass, lat, lon)` returns a name (POI + road, else house number + road, else road, else the first part of `display_name`) or `None` on any network/parse/no-name outcome -- never a distinction between "failed" and "nothing there", so callers always just retry later. Only a place's coordinates ever leave Home Assistant.
- **`routes.py`** - Pure-Python (stdlib only) favorite-drives ("routes") logic: a repeated start->end place pair becomes a route a drive can be compared against, Strava-segment style. `build_routes(drives)` groups non-micro drives by `(start_place_id, end_place_id)` (start must differ from end); a pair needs `MIN_ROUTE_DRIVES` (3) or more to become a route. Drives on the same pair can still take different paths, so each pair is split into **variants** by `split_variants`: a routed drive's cells are its `road_heat.track_cells` cells coarsened from `BASE_LEVEL` (21) to `COARSE_LEVEL` (18, ~110 m) via `coarsen_cells`; drives are grouped greedily, in time order, against each existing variant's *first* (representative) drive's cell set by `jaccard` similarity (>= `VARIANT_JACCARD_THRESHOLD`, 0.6) -- not a running centroid, so a variant's identity doesn't drift. A drive with no track joins the pair's largest variant for timing but never splits or creates one. A variant that ends up under `MIN_ROUTE_DRIVES` folds into the pair's overall largest variant rather than existing on its own; surviving variants are numbered 1-indexed by their earliest drive. `compute_route_stats(drives)` computes fastest/average/slowest elapsed and moving time (ignoring `None`s), energy-weighted average mi/kWh, average temperature, the last drive's timestamp, and a per-drive `DriveRouteStat` (`rank` 1=fastest, `vs_avg_pct`, `outlier`): a drive whose elapsed time exceeds `OUTLIER_MEDIAN_FACTOR` (3x) the pair's median is excluded from the aggregate stats and left unranked, but still listed, flagged `outlier=True`. `route_label(start_label, end_label, variant)` is `"A -> B"`, or `"A -> B (via N)"` once `variant > 1`. **Shared, not per vehicle (schema v10):** a route belongs to no vehicle -- `RouteDriveInput` gains `vin`, drives are identified by `key` (`"vin|drive_id"`, `drive_key()`), and one route groups every car's drives on the same place pair/variant. `RouteStats` is *overall* (flat fields, rank/vs-avg across all cars) plus `by_vin` (`VinRouteStats`: that car's count/best/avg/slowest/mi-kWh); each `DriveRouteStat` has the overall `rank`/`vs_avg_pct` and the within-car `vin_rank`/`vin_vs_avg_pct` (an R2 is never ranked against an R1T). Outliers are still excluded from every aggregate.
- **`analytics_db.py`** - `AnalyticsDatabase`, the SQLite backend (stdlib `sqlite3`, no added dependency) at `.storage/rivian_analytics.db`. One DB for all vehicles, `vin` column on every table. Bulk children (`chunks`, `weather_samples`, `speed_bins`, charge-curve `samples`) are JSON columns, not child tables, since they're only ever read as a whole set for one parent row. Routes live in their own `drive_tracks` table (full track plus a ≤150-point preview, one row per drive), never loaded into the hot cache. `active_drive`/`active_track_chunks` hold the mid-drive checkpoint. `finalize_drive` writes the drive, writes its track and clears the checkpoint in one transaction. Construction does no I/O — `setup()` is executor-bound — and **every method raises if called on the event loop thread**. Schema version lives in `PRAGMA user_version` (currently 14). New DDL goes in both `_SCHEMA_SQL` and `_MIGRATIONS`.
  - **Inferred sessions (no schema change):** `dcfc_sessions.source` may be `'inferred'`: a charge the battery-level history shows that nothing recorded (older data Rivian no longer stores). `DriveStore.async_infer_charging_sessions()` (real vehicles only; `None` for demo or with no `{vin}-battery_level` statistics) reads that sensor's statistics through `statistics.async_soc_history` (hourly from the earliest drive/session, at most 730 days, 5-minute over the last ~10 days; built on `statistics.async_soc_points`, which `websocket_api._soc_timeline_for_store` shares for its 5-minute-with-hourly-fill), runs `detect_charge_spans` against the recorded intervals *excluding* inferred rows (`charging_session_intervals(vin, exclude_inferred=True)`) plus drive ends, and `AnalyticsDatabase.replace_inferred_sessions` swaps the VIN's inferred set in one transaction. `session_id` is `inferred:<vin>:<int start_ts>`; `lat`/`lon` come from `last_drive_end_location` (the latest drive ended before the span, within 7 days, else NULL) so the place resolves; power/energy are 0 when unknown (an `unreported` AC span), shown as None by the payload. A span overlapping a non-inferred row is skipped (inferred never replaces a real/live/backfill/rivian/demo row), and an id in meta `inferred_deleted:<vin>` (JSON list, appended by `delete_dcfc_session` when it removes an inferred row) is never re-added. It runs from `__init__._async_charging_history_job` (after the Rivian import, nightly) and the `rivian.infer_charging_sessions` service (`vin` optional, not admin-only), and fires `rivian_analytics_updated` when the stored set changed. Because stored inferred sessions are in the recorded intervals, `soc_timeline`'s `detected` no longer reports them; detection still covers charges not yet stored.
  - **Schema v14 (charging-session temperatures):** `dcfc_sessions` gains nullable `outside_temp_f` and `battery_temp_f` (also on `ChargingSessionRecord`; the upsert keeps them add-only via `COALESCE`). `battery_temp_f` is the mean of the vehicle's `batteryTemperature` while charging (the tracker collects it whenever reported, else from DC samples' `battery_temp_f`); Rivian doesn't report it for every vehicle (not for the user's R1), so it is often NULL. `outside_temp_f` is filled by `DriveStore.async_fill_session_temperatures`: located, non-demo sessions with no value (`sessions_needing_outside_temp`), grouped by ~11 km tile and <=31-day window, one Open-Meteo archive request per window (skipped for sessions newer than `SESSION_WEATHER_RECENT_DAYS` = 5, which the archive lags), the forecast API's `past_days` (`weather.async_get_recent_hourly_temperatures`) for whatever is still missing; `battery_analytics.mean_hourly_temp` averages the hours within 30 min of the session (nearest hour within 90 min for a short one). At most `SESSION_WEATHER_MAX_REQUESTS` (20) requests 1 s apart per run; it runs in the background after each located session and in `__init__._async_charging_history_job` (shortly after setup, then nightly). Demo sessions get made-up values from `demo.demo_session_temps`. `rivian/charging/sessions` adds `charge_type` (`'dc'|'ac_l2'|'ac_l1'`, AC below `AC_L1_MAX_KW` = 2 kW average is L1; `battery_analytics.charge_type`), `charge_type_label` (`DC Fast`/`AC L2`/`AC L1`), `inferred` (source is `'inferred'`; its unknown power/energy are `null`), `is_home_charge` (`is_home`, brand `home`, the place's category `home` or its zone `zone.home`), `place: {id, label, category}`, `outside_temp_f`, `battery_temp_f` (column, else the mean of the samples'), and an AC session's `max_power_kw` is raised to `battery_analytics.peak_from_soc_samples` (fastest >=15 min stretch of its coarse SoC trace) when higher. The Charging card's history columns are Date, Vehicle, Place, Type, Battery, kWh, Peak, Avg, Battery temp, Outside, Duration. Above the table, two segmented filters (remembered in localStorage `rivian-charging-history-filters`) apply on top of the battery-chart zoom and the scorecard chip: Type All / Home (`is_home_charge`) / L1-L2 (kind `ac`) / Fast (kind `dc`), and Timeframe Week / Month / Year / All (last 7/30/365 days), with a session count (`historyTypeMatches`, `historyFrameStart`, `filterHistory`). An inferred row carries a dashed "Inferred" badge and muted styling, and the Battery level chart draws it with the same dashed outline as detected spans.
  - **Schema v13 (charging stations + capacity history):** `dcfc_sessions` gains nullable `vendor`, `network`, `station_name`, `station_version`, `charger_max_kw`, `is_home` (0/1/NULL) and `rivian_txn_id` (unique per VIN when set); `ChargingSessionRecord` carries the same fields and `source` may now be `'rivian'` (and `'inferred'`, see above). Sessions are oldest first across vehicles; `days` limits to sessions ending in the last N days (counts follow the same window). The plain counts cover every session (DC and AC); the `dc_` variants count fast charges only. `expected` is the vehicle's reference pack over the same SoC range; `pct_of_expected` = expected minutes / actual minutes x 100 (100 = as fast as the reference, higher is faster). Deleting a session (AC or DC) is the existing admin-only `rivian/charging/delete_session`. `start`/`end` (epoch seconds, a zoom window: sessions ending at/after `start` and starting at/before `end`; combinable with `days`) and `brands` (keep only those `brand` keys, `home` included) filter the sessions and the counts alike. With `drive_ends` (the handler passes `DriveStore.async_drive_end_times`): a rise is DC only if a drive ended within `DETECT_DC_DRIVE_GAP_S` (1 h) before or during it, a DC-speed rise with no drive is AC `unreported` with no `avg_power_kw` (a level reached while Home Assistant got no updates), and two detected spans with no drive, no recorded session and a held level between them, at most `DETECT_MERGE_GAP_S` (8 h) apart, are joined into one `unreported` AC charge whose end is extrapolated at the rate before the gap (capped at the next reading). Seen live 2026-09-24: every Rivian entity went silent 02:03-07:27 (the live subscription stalled, then reconnected with an `unavailable` blip) while the car charged to its 95 % limit; the update status and power state show it was neither an OTA install nor sleep), `kind` `'dc'` when the rise's average power on the pack capacity reaches 15 kW. Display-only: the card draws them with a dashed outline (DC spans densely hatched, AC sparsely ///) and they never enter the scorecard or history. A real vehicle reads its `{vin}-battery_level` sensor's recorder statistics (resolved through the entity registry; `mean` per 5 minutes for a window of 10 days or less, per hour beyond); a demo vehicle, or one with no statistics, is synthesized from its drives and sessions. At most ~2000 points per vehicle; `time_in_band` values are fractions of covered time.

Reads the stored `capacity_history` (all of it, back to the first day; seeded from the sensor's long-term statistics and drives, refreshed daily) plus today's live `{vin}-battery_capacity` sensor value (larger than the stored day replaces it; no temperature); the original is the first day's value (the pack's nominal with none); `pack` comes from `pack_for(model, capacity, model_year)`; projected full range is the day's median `end_range_mi / end_soc * 100` over drives with `end_soc >= 10`. The frontend colors points by `temp_f` and states `temp_source`.

**Custom services** (defined in `custom_components/rivian/services.yaml`, handled in `__init__.py`):
- `rivian.backfill_drive_history` (`vin` optional, `days` 1-365, `dry_run` default true, `tracks` default true) - reconstructs drive/efficiency history, and optionally GPS routes, from recorder data. It never modifies the recorder, and a dry run writes nothing at all.
- `rivian.create_efficiency_dashboard` (`title`, `icon`, `url_path`; default "Rivian" at `rivian-dashboard`) - generates and registers the tabbed Rivian dashboard.
- `rivian.set_vehicle_picture` (`url`, optional `vin`) - downloads an image once and stores it as the vehicle's picture.
- `rivian.rebuild_heat_map` (`vin` optional) - recounts the road heat map from stored routes for one vehicle or all; only needed after changing Home Assistant's time zone.
- `rivian.recompute_drive_stats` (`vin` optional) - recomputes each drive's track-derived summary stats (moving/stopped time, stop count, climb/descent, robust max speed, highway share) from its stored GPS route; never touches the live-only vehicle-context fields. A thinned (simplified) route gives slightly less accurate stop/climb numbers than a full-detail one.
- `rivian.backfill_weather` (`vin` optional, `days` 1-365 default 365) - fills each stored routed drive's still-empty wind/headwind/precip/pressure/humidity/air-density columns and `expected_kwh` from the Open-Meteo **archive** (`weather.OpenMeteoWeatherClient.async_get_historical_conditions`). Add-only, never for a demo VIN (demo drives carry their conditions in the fixture, computed by `scripts/build_demo_data.py`'s `add_conditions`, seeded by drive id so it never shifts other generated values; `--augment` re-derives them offline from the existing fixture). `DriveStore.async_backfill_weather` groups drives by ~0.1 degree location tile and windows of <=31 days (one request each, 1 s apart, abort after 3 failures in a row), and `_async_seed_weather_once` runs it once per VIN in the background after upgrade (stamped as above only when no request failed). Live samples (`DriveTracker._async_sample_weather`) now also carry the wind/pressure/precip/humidity fields, served from the same Open-Meteo request as the temperature (`async_get_current_conditions` reads that cache; `async_get_current_temperature` is unchanged, requesting wind in mph).
- `rivian.fit_energy_model` (`vin` optional) - refits the anchored energy model (`energy_model.py`) from recent routed drives now instead of waiting for the nightly refit.
- `rivian.import_charging_history` (`vin` optional) - imports the Rivian app's completed charging sessions now (bypassing the once-a-day guard), matches/enriches/inserts them, runs the OSM station lookup for fast charges and refreshes the capacity history (see `charging_history.py`). Real vehicles only. Translations live in `services.yaml`, `strings.json` and `translations/en.json`.
- `rivian.infer_charging_sessions` (`vin` optional) - stores the charges the battery-level history shows but nothing recorded as `source='inferred'` sessions (see schema v14 notes above). Real vehicles only. The service always re-scans the whole history (`full=True`); the automatic runs scan it only once per VIN (meta `inferred_scan:<vin>` = `{version, through}`, redone when `INFER_VERSION` changes), then nightly re-check just the last `INFER_RESCAN_DAYS` (10) before the previous run, replacing only inferred rows starting after its first `INFER_OVERLAP_DAYS` (1) (`replace_inferred_sessions(vin, sessions, since_ts)`).
- `rivian.snap_route_gaps` (`vin` optional) - fills recorded GPS dropouts by snapping them to OpenStreetMap roads (see `road_snap.py`). `DriveStore.async_snap_gaps()` runs the same work as a background task after each finalize (when the drive has a track), after a track backfill, and once after first load; a gap that a network/parse failure left unresolved is retried on the next pass, never marked `'none'`. If any fill landed on a drive whose road heat was already counted, the affected month is recounted (`rebuild_heat`) once, since a plain `update_heat()` skips already-counted drives.
- `rivian.rebuild_places` (`vin` optional) - re-clusters frequent drive start/stop spots into places (seeded from HA zones) and reassigns every drive's start/end place; fires `rivian_analytics_updated` afterward. Also run once after a (non-dry-run) backfill writes drives.
- `rivian.rebuild_routes` (`vin` optional) - re-groups repeated start->end place pairs into routes and path-similarity variants, recomputing each route's fastest/average/slowest stats; fires `rivian_analytics_updated` afterward. Also run once after a (non-dry-run) backfill writes drives, and after a place merge/edit (places changing can merge, split or dissolve a route).
- `rivian.create_demo_data` (no fields; **admin-only**, registered with `async_register_admin_service`) - installs (or replaces) the two demo vehicles described under `demo.py`, then updates the picker and regenerates the Rivian dashboard.
- `rivian.delete_demo_data` (`vin` optional; **admin-only**) - removes every demo vehicle (or one) completely.

Service/field translations must stay in sync between `services.yaml` and `strings.json`/translation files - keep them updated together when changing either.

**Retention:** drives and idle-drain events are pruned to `analytics_retention_days` (config-entry option, default 365, `0` = forever) on a 24-hour timer plus once shortly after setup. Charging session summaries (DC and AC) are kept; DC curves outside the newest 50 are blanked, AC sessions keep their coarse SoC points. Routes have their own options, all in `config_flow.py`:
- `track_capture` (default on)
- `track_retention_days` (default 365, `0` = as long as the drive)
- `track_full_detail_days` (default `0` = never thin; older routes are simplified to ~10 m)

`chart_window_days` (default 365) sets how far back the charts reach. `place_geocoding` (default on) controls whether unnamed, frequently-visited auto places are reverse-geocoded via Nominatim (see `geocode.py`); off leaves them with a numbered label until named by hand. Long-term statistics are never pruned.

**Two invariants worth knowing before touching this subsystem**, both with regression tests guarding them: nothing on the synchronous path may reach SQLite (`tests/test_analytics_db.py` poisons the DB and exercises every sync accessor and sensor property), and sensor attributes must stay under 16,384 bytes or the recorder silently drops them (`tests/test_sensor.py` asserts the serialized size). The bulk keys are also listed in `recorder.py`'s `exclude_attributes` as defence in depth.

### Vehicle Control

Remote commands require:
- 2FA enabled on Rivian account
- Bluetooth pairing (one-time, in-vehicle; requires a Bluetooth adapter on the HA host or an ESP32 BT proxy, BT 4.2+) - not available on Gen2 (2025+) vehicles
- Vehicle in "Park" gear
- Optionally restricted by Home Assistant zones

Commands flow through `VehicleCoordinator.send_vehicle_command()` which:
- Wakes vehicle if sleeping
- Uses enrolled phone credentials from config entry options

### Platform Files

Each platform in `PLATFORMS` (`__init__.py`) has its own module that:
1. Defines entity descriptions specific to that platform
2. Implements `async_setup_entry()` to create entities
3. Extends the appropriate base entity class

## Key Dependencies

- `rivian-python-client[ble]==2.0.0` - Core API client (includes BLE support for pairing)
- `homeassistant>=2025.1.0` - Home Assistant core

That's deliberately the whole list. The analytics store uses stdlib `sqlite3`, so it adds no dependency. Be reluctant to add any: HA's container is Alpine/musl, so anything with C extensions needs a `musllinux` wheel for aarch64/armv7 or the integration fails to load on HAOS.
